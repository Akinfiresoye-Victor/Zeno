## 2. Architecture Rules & Engine Redesign

### Rule A: Two Separate Areas, Two Separate Histories (Assistant vs Agent Workspace)
1. **Independent State & Thread Trees**:
   - Split `sessions` into two strictly isolated stores:
     - `assistantThreads`: Conversational threads, question/answer history, document summaries.
     - `agentRuns`: Autonomous task runs with execution plans, checklist state, process logs, and workspace manifests.
   - Stored in separate files: `zeno/assistant_chats.json` and `zeno/agent_runs.json` (with backward-compatible automatic migration from existing `zeno/chats.json`).
2. **Always-Available Assistant Chat**:
   - The user can compose and send messages in "Assistant" at any time, even while one or more agent runs are actively executing.
   - The "Send" button in Assistant is never disabled or replaced by "Stop" during an agent run.
3. **Cross-Area Read-Only Agent Inspector**:
   - Assistant has a dedicated read-only context tool (`inspect_agent_run(run_id)`) allowing it to read the agent's checklist, live logs, created files, and error diagnostics.
   - When asked "why did step 4 fail?" or "where is the server code?", the Assistant queries the run record directly and provides an analytical answer without altering the run's state.
   - Any modifications or task revisions requested by the user are routed to the Agent Workspace as a new task or "revise step" directive.
4. **Independent Scoped Stop**:
   - Stopping an agent run applies strictly to that specific `run_id`. It cancels that run's task and kills its process tree without blocking or interrupting Assistant chat.
5. **Multi-Run Queue Engine**:
   - Allow multiple runs to be created.
   - Configurable concurrency limit (default: 1 active run, remaining queued).
   - Live visual queue in the Agent Workspace showing queued, running, paused, and completed runs.

### Rule B: Workspace Folder Rule (Python-Enforced)
1. **Pre-Task Project Isolation**:
   - Before any task step starts, the engine creates exactly one isolated project folder inside the configured workspace root (default: `~/Documents/ZenoWorkspace/<project-name>`).
2. **Creative, Descriptive Folder Naming**:
   - Folder names are generated by asking the model for a 2–4 word descriptive title followed by strict Python sanitization.
   - Format: lowercase, hyphen-separated, maximum 32 characters, no task-sentence slugs.
   - Examples: `car-dash-tkinter`, `mathlab-core`, `pulse-shop-api`.
   - Collision resolution: If the directory exists, Python appends a short hex suffix (e.g. `mathlab-core-a1`).
3. **UI Folder Renaming & Inspection**:
   - The project folder name is displayed prominently in the Agent Workspace header, with an inline rename modal allowing the user to rename the folder before or during execution.
4. **Strict Filesystem Sandboxing**:
   - `write_file`, `append_file`, `create_document`, and dev tools are strictly forbidden from writing anywhere outside the project folder. Any attempted write outside is vetoed by Orchid before execution.
   - Reading files outside is permitted only for user-provided files within allowed directories (`Documents`, `Downloads`, `Desktop`).

### Rule C: Task Engine with Python Checklist as the Source of Truth
1. **Machine-Readable Checklist (`checklist.json`)**:
   - Created in the project folder root: `<project>/checklist.json`.
   - Schema per step:
     ```json
     {
       "id": "step-1",
       "title": "Initialize virtual environment and install requirements",
       "dependencies": [],
       "status": "verified",
       "attempts": 1,
       "max_attempts": 3,
       "evidence": {
         "files_created": [".venv", "requirements.txt"],
         "command_exit_codes": [0],
         "test_results": null,
         "screenshot_path": null
       },
       "orchid_verdict": {
         "verdict": "ALLOW",
         "rule": "allow_venv_creation",
         "reason": "Virtualenv setup inside project folder approved."
       }
     }
     ```
   - Step statuses: `pending`, `running`, `verified`, `failed`, `needs_revision`, `cancelled`.
2. **Python Verification Gating (Model Cannot Self-Certify)**:
   - A step transitions to `verified` ONLY when Python checks confirm:
     1. Required output files exist and are non-empty.
     2. Executed commands returned exit code `0`.
     3. Automated tests for that step pass (if tests are defined).
     4. Orchid security guard explicitly approved all actions in the step.
3. **Strict Dependency Gating**:
   - A step cannot begin execution until every step listed in its `dependencies` array is in the `verified` state.
4. **Intelligent Step Revisitation & Jump-Back**:
   - If an error or bug in an earlier step is discovered at step 5 (e.g. bug in step 2's factorial function):
     - Step 2 is marked `needs_revision`.
     - The engine runs step 2 with revision instructions.
     - Following step 2's completion, the engine follows the dependency graph to re-verify *only* steps that depend on step 2.
     - If no downstream steps depend on step 2, the agent jumps directly back to step 5.
     - Every jump-back is logged to the checklist with a specific reason.
5. **Retry Limits & Pauses**:
   - Each step allows up to 3 attempts. Upon reaching the limit, the step is marked `failed`, the run is paused, and the user is presented with choices: `Retry`, `Skip` (if allowed), `Revise earlier step`, or `Stop`.
6. **Checkpoint Recovery**:
   - `checklist.json` is synced to disk after every step transition. If the app or machine crashes or network drops, opening the run resumes seamlessly from the last verified step without repeating completed work.

### Rule D: Error Handling, Classification & Retries (Fixing SSL EOF)
1. **Granular Error Classifier**:
   - Every failure is parsed into one of six distinct categories:
     1. `TRANSIENT_NETWORK`: SSL EOF (`[SSL: UNEXPECTED_EOF_WHILE_READING]`), connection reset (`WSAECONNRESET`), socket timeout, DNS failure.
     2. `RATE_LIMIT`: HTTP 429, resource exhausted, quota exceeded.
     3. `SERVER_OVERLOAD`: HTTP 503, service unavailable, high demand.
     4. `AUTHENTICATION`: HTTP 401, 403, invalid API key.
     5. `BAD_REQUEST`: HTTP 400, context window exceeded, invalid schema.
     6. `TOOL_COMMAND_ERROR`: Non-zero exit code, compiler/syntax error, test failure.
2. **Exponential Backoff with Jitter**:
   - For `TRANSIENT_NETWORK`, `RATE_LIMIT`, and `SERVER_OVERLOAD`:
     - Up to 5 retry attempts with exponential intervals: `2s`, `4s`, `8s`, `16s`, `32s` (plus randomized jitter).
     - Live status line displayed in UI: `"Gemini connection dropped. Retry 2 of 5 in 8s..."`
3. **Explicit Provider / Model Switching**:
   - If retries on the primary model are exhausted and the user has configured keys in Key Slot 2 or 3 (e.g. Claude or OpenRouter), prompt the user in the UI with a clear dialog: `"Gemini is unavailable. Switch to Claude 3.5 Sonnet to continue?"`
   - Never switch models or providers silently.
4. **Zero Work Loss Guarantee**:
   - A model error NEVER marks a step completed. The step remains in `failed` or `running` state.
   - Any partial outputs, drafts, or code generated before the error are saved into `<project>/.drafts/` so progress is never discarded.

### Rule E: Flexible Command Execution (No Hardcoded Commands)
1. **Dynamic Virtual Environment Engine**:
   - When a project starts, the engine initializes a dedicated virtual environment inside `<project>/.venv`.
   - Generates/updates `<project>/requirements.txt` and runs `pip install -r requirements.txt`.
   - All subsequent commands run directly using the venv's Python binary:
     - Windows: `<project>/.venv/Scripts/python.exe`
     - Linux/macOS: `<project>/.venv/bin/python`
   - Eliminates fragile activation scripts.
2. **Polyglot Stack Support**:
   - Supports any language runtime: Node.js (`npm`, `npx`, `node`), Python (`django-admin`, `flask`, `pytest`, `uvicorn`), etc.
3. **Long-Running Server Job Supervision**:
   - Servers (Django, Flask, Vite, etc.) run as tracked background jobs with registered PID.
   - Stdout and stderr stream directly to `<project>/.zeno_server.log`.
   - Verification health check: The engine performs an automated HTTP GET check against the server URL (expecting HTTP 200/302) before considering the startup step verified.
4. **Visual Evidence Capture**:
   - Web apps: Headless browser screenshot (Playwright running in the venv) captured and saved to `<project>/evidence/screenshot_web.png`.
   - Desktop GUI apps (tkinter, PyQt): Window capture via `mss`/`Pillow` saved to `<project>/evidence/screenshot_gui.png`.
   - Evidence is attached to `checklist.json` and shown in the UI inspector.
5. **Reliable Process Tree Kill**:
   - When stopping a job or cancelling a run, the engine kills the entire process tree:
     - Windows: `taskkill /PID <pid> /T /F` and `psutil.Process(pid).children(recursive=True)`
   - Marks jobs as `stopped_by_user` or `finished`.
6. **Configurable Command Timeouts**:
   - Default timeout per command: 60s (extensible up to 300s for builds/installs).

---

### Rule F: Orchid Safety Review (Real, Transparent, Non-Bypassable)
1. **Every Action Inspected**:
   - Every file write and command execution passes through Orchid before execution.
   - Returns a structured verdict: `ALLOW`, `DENY`, or `ASK_USER`, accompanied by the matched rule name and detailed justification.
2. **Layered Rule Matrix**:
   - **DENY (Prohibited)**:
     - Writing or deleting files outside the project folder.
     - System directory commands (`C:\Windows`, `/etc`, `rm -rf /`, formatting drives).
     - Registry modifications, PowerShell execution policy bypasses.
     - Downloading and executing unverified external scripts.
   - **ALLOW (Pre-approved safe)**:
     - `pip install` inside the project's `.venv`.
     - `python` execution using the project `.venv` interpreter inside the project directory.
     - Git operations on feature branches (`git status`, `git diff`, `git commit`).
     - Running test suites (`pytest`, `npm test`).
   - **ASK_USER (Escalated review)**:
     - Port bindings on public interfaces (`0.0.0.0`).
     - Launching external desktop applications.
     - Modifying non-standard files.
3. **Transparent Audit Display**:
   - The Orchid panel displays:
     - Action proposed: `shell_run: .venv/Scripts/python.exe manage.py runserver`
     - Verdict: `ALLOW` (Muted green badge)
     - Matched Rule: `rule_project_venv_execution`
     - Justification: `Command executes inside isolated project directory using dedicated virtual environment.`
   - No generic "Verified safe action" without context.
4. **Non-Bypassable**:
   - Orchid runs in the Python security kernel before subprocess/file I/O. Prompt injection or model instructions cannot override Orchid decisions.

---

### Rule G: Complete Visibility & UI Inspection
1. **Single Run Timeline**:
   - Shows all steps with status icons, elapsed time, retry attempts, Orchid verdict badge, and jump-back events.
2. **Real-Time Streaming Jobs Panel**:
   - Displays all active and completed processes with PID, command line, status badge, execution duration, live streaming stdout/stderr, and individual Stop button per job.
3. **Real Project Tree in Files Panel**:
   - Interactive tree view reflecting the actual project folder on disk.
   - Click a file to open it in the in-app File Viewer.
   - "Reveal in file explorer" executes `explorer /select,"<absolute_path>"` on Windows.
4. **Clickable File Mentions in Chat**:
   - File mentions in Assistant chat and Agent logs are rendered as interactive links that open the file in the in-app viewer.
5. **Decoupled Neural Animations**:
   - Remove disruptive animations ("Neural Reasoning Matrix") from critical data views, ensuring logs and checklists are never obscured.

## 3. UI Redesign Architecture & Design Tokens

### Modern, Restrained Design System
- **Theme**: Dark neutral theme inspired by modern developer tools (near-black `#09090D`, slate greys `#121217`, `#1B1B22`, `#262630`).
- **Accent**: Refined indigo/violet accent (`#6366F1` / `#818CF8`) replacing garish neon blues and greens.
- **Semantic Palette**:
  - Success: Muted emerald (`#10B981` text, `#064E3B` bg).
  - Warning: Warm amber (`#F59E0B` text, `#78350F` bg).
  - Error: Clean rose/red (`#EF4444` text, `#450A0A` bg).
  - Neutral / Info: Slate (`#94A3B8`).
- **Contrast**: WCAG AA compliant contrast ratio (>4.5:1 for normal text, >3:1 for large text).
- **Typography**:
  - UI Font: Clean sans-serif system stack (`Inter`, system-ui, -apple-system).
  - Monospace: `JetBrains Mono`, `Fira Code`, monospace for logs, code, PIDs, and tokens.
- **Design Tokens File**: `src/theme/tokens.ts` defining colors, spacing, borders, shadows, and typography tokens. All components will import and use these tokens.

## 5. Verification Test Plan (10 Required Verification Suites)

Before reporting done, the following 10 test suites will be authored and verified:

1. **Checklist Engine Tests (`tests/test_checklist_engine.py`)**:
   - Verifies step dependencies (step cannot run until dependencies are verified).
   - Verifies Python verification gating (model cannot self-certify).
   - Verifies jump-back logic (marks earlier step `needs_revision`, re-verifies dependent steps only, returns to caller).
   - Verifies retry limits (pauses after 3 failures).
   - Verifies checkpoint save and resume from last verified step.
2. **Error Classifier & Retry Tests (`tests/test_error_classifier.py`)**:
   - Simulates `[SSL: UNEXPECTED_EOF_WHILE_READING]` and verifies it is classified as `TRANSIENT_NETWORK`.
   - Verifies exponential backoff timing and that the step is NEVER marked complete on model failure.
   - Tests HTTP 429, 503, 401, and tool error classification.
3. **Folder Naming & Sanitization Tests (`tests/test_folder_naming.py`)**:
   - Tests model-generated name sanitization (lowercase, 2-4 words, hyphens, max 32 chars).
   - Tests collision avoidance (appends suffix if folder exists).
   - Tests stripping of dangerous characters (`..`, `/`, `\`, quotes).
4. **Orchid Safety Rule Tests (`tests/test_orchid_rules.py`)**:
   - Verifies destructive commands (`rm -rf /`, formatting drives, registry edits) are DENIED.
   - Verifies writing outside project folder is DENIED.
   - Verifies `.venv` creation and `pip install` inside project are ALLOWED with matched rule name.
   - Verifies unknown commands trigger `ASK_USER`.
5. **End-to-End Run 1 (Django Server)**:
   - Full execution: creates creative project folder, initializes `.venv`, installs requirements, creates Django app, launches server as background job, runs HTTP health check (200 OK), takes headless screenshot, stops server, marks run complete.
6. **End-to-End Run 2 (Tkinter Car Game)**:
   - Full execution: creates project folder, sets up `.venv`, writes tkinter game code, starts GUI app, captures window screenshot evidence, stops process, verifies run.
7. **Assistant Concurrency Test**:
   - Starts Run 1, sends a prompt in Assistant while Run 1 is executing, verifies Assistant replies promptly without blocking or state interference.
8. **Process Tree Termination Test**:
   - Starts a background job with multiple child processes, invokes Stop, and verifies with `psutil` that all child processes have completely exited.
9. **Simulated Network Drop Test**:
   - Simulates network disconnection during step execution, verifies live retry status in UI, confirms step remains uncompleted, restores network, and verifies successful completion.
10. **Jump-Back Dependency Test**:
    - Generates a 5-step plan where Step 5 depends on Step 2.
    - Injects a bug into Step 2 during Step 5 execution.
    - Confirms jump back to Step 2, re-verification of only dependent steps, and seamless return to Step 5.
